The problem

A reader may know the question they want to ask without knowing the words used in a long PDF. I built a retrieval-augmented generation application that finds related passages and passes them to a language model as context for an answer.

Engineering decisions

Keep document embeddings local

PDFPlumber extracts the document text. LangChain splits it into 1,500-character chunks with 200 characters of overlap, and a local MiniLM model converts the chunks to embeddings. The model is cached across interactions, and a file hash avoids repeating ingestion for the same upload during a session.

Local embedding removes an external call from that stage. Answer generation still sends the retrieved passages and question to Groq, so this is not a fully local or offline document assistant.

Use a small, inspectable retrieval path

The application embeds the question, compares it with the document vectors using cosine similarity, and passes the top three chunks to the answer-generation prompt. In-memory retrieval keeps the prototype straightforward; it does not provide a persistent multi-user document index.

Constrain the answer, while acknowledging the limit

The prompt asks the model to answer from the retrieved text, keep its response concise, and acknowledge when the context does not contain the answer. These instructions reduce unsupported-answer risk but do not guarantee factual correctness. Retrieval can miss a relevant passage, and a model can still produce an unsupported answer.

Try the implementation

The public repository contains the application and setup instructions. With its dependencies and your own Groq credential configured, run:

streamlit run AI_PDF_Chatbot.py

Use a non-sensitive PDF, ask a question with an explicit answer in it, and compare the response with the source passage. Then ask a question the document cannot answer. These are useful inspection steps, rather than a published accuracy benchmark.

Outcome & scope

The project implements the full PDF question-answering loop: upload, extraction, indexing, retrieval, prompt construction, and response display. The main interface is Streamlit. The Flask prototype explores a separate university FAQ knowledge base using SPARQL retrieval and answer rewriting.

Scanned PDFs need an OCR path beyond the current text extraction approach. Persistent storage, user isolation, and a measured retrieval-quality evaluation would be needed before treating this prototype as a shared production service.

Stack: Python, Streamlit, LangChain, PDFPlumber, sentence-transformers, scikit-learn, NumPy, Groq, and Flask.
